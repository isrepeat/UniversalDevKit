# UniversalDevKit — оставшиеся задачи

Состояние на 12 октября 2026 года. Список продолжает первоначальный архитектурный обзор (пункты 1–8). Выполненные изменения учитываются по текущему рабочему дереву, включая ещё не закоммиченные доработки.

## 1. Контракт CMake-пакета

- [x] Проверять конфликтующие Static/Dynamic-варианты в CMake для каждого consumer, включая транзитивные внутренние зависимости DLL и установленный экспорт.
- [x] Проверить отказ для x64-пакета у Win32-consumer, недоступного варианта и отсутствующей Debug-конфигурации. Полная матрица ABI/архитектур остаётся в пункте 5.
- [x] Проверить пакет с ограниченным составом: доступный компонент собирается и запускается, исключённый обязательный компонент отклоняется.

Уже реализовано: одинаковые явные имена targets до и после установки; автоматические признаки COMPONENTS; выбор компонентов и вариантов с раскрытием зависимостей; отключение установки; удаление ARCH_INDEPENDENT; SameMinorVersion для 0.x; отдельные имена Debug-бинарников.

## 2. Единое описание компонентов и платформ

- [x] Добавить единый контракт requirements/platformRequirements для C++17/20/23, threads и системных библиотек; Diagnostic получает Threads из JSON.
- [ ] Расширять контракт по необходимости: внешние пакеты, RTTI и исключения требуют отдельных правил и проверок.
- [x] Проверить Windows-исходник и системную библиотеку в MSBuild/CMake, а также отказ для неподдерживаемой ОС.
- [ ] Проверить реальные платформенные реализации на Linux/Android с их toolchains.
- [ ] Добавить проверенные Linux/Android toolchains и presets. Поля реестра сами по себе не подтверждают поддержку платформы.
- [x] Проверить новый тестовый компонент: генерацию проектов и solution, интерактивный Connect Shared/Static/Dynamic, сборку и запуск consumer, установку и использование CMake-пакета.

Уже реализовано: списки файлов и межкомпонентные зависимости берутся из JSON; обычному компоненту не нужен отдельный CMake-файл; supportedPlatforms и platformSources; создание отсутствующих библиотечных проектов и добавление новых проектов в solution. Новые записи solution пока размещаются на верхнем уровне.

## 3. Передача зависимостей

- [ ] Дополнить проверки реальными сборками более сложных графов: публичные и внутренние зависимости, ромб, транзитивные DLL, несколько consumer и переключение режимов.
- [ ] Проверить системные зависимости и публичные требования после установки пакета на Linux/Android.

Основной механизм реализован: Shared/Static/Dynamic, visibility/linkage, передача статических библиотек финальному линкеру, import-макросы, транзитивные DLL и Threads::Threads. Получение DLL использует фактический TargetPath.

## 4. Состояние компонентов между бинарными модулями

- [x] Добавить политику stateScope module/process и обязательное Dynamic-подключение process-компонентов.
- [ ] Назначать политику конкретным компонентам с состоянием согласно требованиям их API.
- [x] Поддержать общую DLL/SO через linkage=dynamic, включая Shared/Static-потребителей.
- [x] Проверить общий счётчик сервиса в приложении и двух плагинах.
- [ ] Проверить конкурентное логирование и время жизни сервиса при выгрузке плагинов.
- [ ] Документировать, что проверка вариантов подключения не обеспечивает единственный экземпляр статического состояния на процесс.

В Diagnostic остаётся локальный статический mutex. При включении реализации в несколько DLL возможны независимые экземпляры; аналогичная проблема возникнет у кешей и регистров обработчиков.

## 5. Совместимость бинарников и изоляция сборок

- [ ] Определить поддерживаемую матрицу Windows: архитектура, toolset, CRT /MD или /MT, Debug/Release.
- [ ] Определить матрицу Linux: архитектура, компилятор, стандартная библиотека и минимальная системная среда.
- [ ] Определить матрицу Android: ABI, версия NDK, минимальный API level и C++ runtime.
- [ ] Учитывать параметры совместимости в каталогах сборки и выборе пакетных бинарников, чтобы разные варианты не перезаписывали друг друга.
- [ ] Проверять совместимость consumer с бинарным пакетом и выдавать понятные ошибки.
- [ ] Закрепить условия C++ ABI для публичных интерфейсов с типами STL, включая Log(std::string_view). Решить необходимость стабильного C-интерфейса только при появлении соответствующего сценария использования.

## 6. Экспорт символов и версии ABI

- [ ] Выделить общую схему API-макросов компонентов и явного экспорта для Linux/Android при скрытой видимости символов.
- [ ] Настроить и проверить видимость публичных и внутренних символов DLL/SO.
- [ ] Определить политику API/ABI и правила VERSION/SOVERSION для SO.
- [ ] Согласовать версию исходников, CMake-пакета, NuGet и AAR с этой политикой. SameMinorVersion — текущая проверка версии CMake, а не доказательство бинарной совместимости.

## 7. NuGet и Android-пакеты

- [ ] Добавить пакетные проекты в PackageProjects без копирования исходников в отдельную реализацию.
- [ ] Для native NuGet реализовать выбор совместимых библиотек, include-пути, линковку, import-макросы и доставку runtime DLL через пакетные props/targets.
- [ ] Определить назначение Android-пакета: C++-потребитель с Prefab-модулями либо Java/Kotlin API с JNI-обёрткой.
- [ ] Для Prefab описать заголовки, библиотеки, ABI и зависимости модулей.
- [ ] Согласовать C++ runtime приложения и всех SO; проверить отсутствие конфликтующих копий runtime.
- [ ] Обеспечить подключение пакетов без checkout UDK и зависимости от внутренних путей !artifacts.
- [ ] Добавить лицензию и необходимые сведения о сторонних зависимостях в выпускаемые пакеты.

## 8. Проверки потребителей и выпуска

- [ ] Включить проверки реестра, Connect и установленного пакета в автоматическую проверку изменений.
- [ ] Расширить проверки переноса пакета на Linux/Android и выбранную матрицу toolchains/CRT.
- [ ] Проверить реальные потребители NuGet/AAR, включая запуск и наличие транзитивных runtime-зависимостей.
- [ ] Проверять заголовки отдельно от исходников и запуск Dynamic-consumer из чистого каталога.

Уже проверено и оформлено скриптом TestCMakePackage.ps1: установка Windows x64 Debug/Release в один prefix, перенос установленного каталога, сборка и запуск отдельного Static/Dynamic-consumer, отказ для неизвестного обязательного компонента. Есть проверки реестра и расчёта зависимостей Connect.
