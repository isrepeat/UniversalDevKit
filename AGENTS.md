## Общие правила

### Формат файлов и способ редактирования

- Генерируемые файлы начинаются комментарием «Сгенерировано <название скрипта>. ...» с указанием источника изменений. В C++ комментарий располагается перед #pragma once; в XML — сразу после обязательной XML-декларации. Файлы с частичной автоматизацией не помечаются как полностью генерируемые.

- Последний байт каждого текстового исходного, конфигурационного и документационного файла обязан быть частью последней содержательной строки: запрещены завершающие `CR`, `LF`, пустые строки и любой trailing whitespace. После изменений обязательно проверять это для всех файлов из объединения `git diff --name-only` и `git ls-files --others --exclude-standard` строгим числовым сравнением последнего байта с `9`, `10`, `13` и `32`.
- Все изменения текстовых файлов выполняются через `apply_patch`; запрещено заменять его записью через PowerShell, Python, shell или другие средства.
- Исключение для генератора: `Scripts/PowerShell/UpdateProjectFilters.ps1` записывает автоматически сформированные `.vcxproj.filters` напрямую, в UTF-8 без BOM и без завершающих CR, LF и пробелов.
- Исключение для генератора: `Scripts/PowerShell/GenerateComponentProjects.ps1` записывает автоматически сформированные `.vcxitems` и `Projects/MsBuild/UniversalDevKit.Sources.targets` напрямую, в UTF-8 без BOM и без завершающих CR, LF и пробелов. Правило использования apply_patch относится к редактированию файлов агентом, а не к работе этих генераторов.
- Единственное исключение: после `apply_patch` разрешено отдельной командой удалить только завершающие байты `CR` и `LF`, не изменяя остальное содержимое файла, если инструмент добавил их и не позволяет сохранить файл без них.

### Язык комментариев и коммитов

- Исполняемые строки и сообщения CMD/PowerShell пишутся на английском языке; комментарии могут оставаться на русском. Точки запуска согласуют UTF-8 консоли и native pipeline; dotnet/MSBuild/NuGet запускаются с английским языком сообщений. Проверка: Tests/Infrastructure/TestScriptEncoding.ps1.

- Комментарии в исходном коде этого репозитория пишутся на английском языке, включая комментарии к этапам методов и тестов.
- Сообщения Git-коммитов создаются на английском языке.

### CMD-скрипты

- `Scripts/PowerShell/Connect.ps1` разрешено напрямую обновлять выбранный `.vcxproj` потребителя для подключения или удаления UniversalDevKit. Исходники не копируются; сохраняются относительные пути и отсутствие завершающих CR/LF.

- Каждый CMD-скрипт должен завершаться паузой, чтобы пользователь мог увидеть статус выполнения. Код завершения основной операции сохраняется до `pause` и возвращается после неё.

### Имена MSBuild

- Внутренние свойства и элементы MSBuild в UniversalDevKit начинаются с двух подчёркиваний `__` и содержат имя UniversalDevKit для снижения риска пересечений с другими импортами.
- Внутренние булевы свойства именуются с `__Has` или `__Is`, отражая смысл флага: `__HasUniversalDevKitHelpers`, `__IsUniversalDevKitSomething`.
- Публичные настройки потребителя сохраняют префикс `UniversalDevKit` без подчёркиваний. Префикс `__` является соглашением именования, а не механизмом изоляции MSBuild.

## C#


### Директивы using

- Директивы `using` располагаются четырьмя блоками в таком порядке: пространства имён .NET/System, сторонние библиотеки, пространства имён этого репозитория, alias-директивы `using X = ...`.
- Блоки отделяются ровно одной пустой строкой. Пустые `using`-блоки не создаются.
- Внутри каждого блока namespace образуют дерево. На каждом уровне сначала располагается родительский namespace, затем все его дочерние namespace; дочерние ветки идут до перехода к следующему соседнему namespace.
- Соседние сегменты namespace на каждом уровне сортируются по длине по возрастанию: более короткий сегмент располагается выше более длинного. При равной длине применяется лексикографический порядок. Например, порядок веток `System` начинается с `System.IO`, затем `System.Text` и его дочерних namespace, затем `System.Windows` и его дочерних namespace, затем `System.Reflection`, затем `System.Diagnostics`.

```csharp
using System.IO;
using System.Text;
using System.Text.Json;
using System.Windows;
using System.Windows.Input;
using System.Reflection;
using System.Diagnostics;
```

## C++

### Расположение исходников

- Иерархия namespace должна полностью отражать иерархию папок исходников. Например, `Includes/Helpers/UniversalDevKit/Helpers/Meta/Utilities/PointerGetter.h` объявляет класс в `universaldevkit::helpers::meta::utilities`, а не в `universaldevkit::helpers::meta`.

- Файлы проектов сборки находятся в `Projects/MsBuild/` и `Projects/Cmake/`; описание пакетов — в `Packages/`.
- Артефакты собственной сборки всегда находятся в `!artifacts/<ОС>-<архитектура>/<система сборки>/<проект>/`, вне каталогов исходников. При компиляции исходников внутри потребителя используются его изолированные каталоги артефактов.

- Публичные заголовки и шаблонная реализация хранятся в `Includes/<компонент>/UniversalDevKit/<компонент>/`, например `Helpers/Math.h` или `DiagnosticTest/Logging.h`.
- Компилируемая реализация и внутренние заголовки хранятся в `Sources/<компонент>/`. Платформенные реализации находятся в `Sources/<компонент>/platform/<платформа>/`.
- Публичные include-пути потребителя — `Includes/Core/` и `Includes/<компонент>/` согласно графу зависимостей. Заголовки подключаются как `<UniversalDevKit/Helpers/Math.h>`; общий корень `Includes/` не передаётся.
- CMake и MSBuild используют единственный экземпляр исходников. Каталоги создаются по мере появления кода; шаблонным хелперам отдельные `.cpp` не требуются.

### Директивы include

- Include-директивы разделяются ровно одной пустой строкой на пять блоков в следующем порядке: соимённый заголовок текущего `.cpp`-файла, сторонние библиотеки, библиотеки этого репозитория, заголовки текущего проекта по относительному пути, STL.
- Первый блок создаётся только если у `.cpp` есть соимённый заголовок. В четвёртом блоке всегда используется относительный путь. Пустые блоки не создаются.
- Во втором блоке находятся только сторонние зависимости; в третьем — библиотеки, написанные в этом репозитории; пятый блок содержит только заголовки стандартной библиотеки C++.
- Внутри каждого блока пути образуют дерево сегментов, разделённых `/`. На каждом уровне сначала располагаются более длинные сегменты; при равной длине применяется лексикографический порядок. Родительский путь располагается перед своими дочерними путями, а дочерняя ветка целиком — до перехода к следующему соседнему пути.

```cpp
#include "PageManager.h"

#include <Helpers.Logging/Logging.h>
#if defined(MOBILECLOCK_XAML_PREVIEWER)
#include <XamlRuntime/RuntimeMarkup/IRuntimeReloadableControl.h>
#include <XamlRuntime/RuntimeMarkup/RuntimeReloadTransaction.h>
#include <XamlRuntime/RuntimeMarkup/XamlParser.h>
#endif
#include <XamlRuntime/RenderEngine.h>

#include "MobileClock.Presentation/Renderer/AnimationRenderers.h"
#include "MobileClock.Presentation/Core/PageTransition.h"
#include "MobileClock.Presentation/Core/Registrations.h"

#include "../CurrentProject/LocalHeader.h"

#include <algorithm>
#include <format>
#include <limits>
#include <vector>
#include <array>
```

### Имена параметров и полей

- Параметры и поля с пользовательским типом именуются по camelCase-имени типа: UpdateState updateState, PageContext pageContext, NavigationRequest navigationRequest.
- Для реализации интерфейса используется суффикс Impl: IPackageInstaller* packageInstallerImpl.
- Это правило действует и для полей, включая поля, инициализируемые конструктором; имена параметра и поля совпадают, когда конструктор непосредственно передаёт параметр полю.

### Сигнатуры методов

- Если сигнатура метода длиннее 160 символов, каждый параметр располагается на отдельной строке.

### Concepts

- Все concepts объявляются в namespace `concepts` внутри пространства имён соответствующего компонента. По возможности они собраны в начале файла; если зависимости требуют другого порядка, namespace `concepts` разрешено открывать в нескольких частях файла.
