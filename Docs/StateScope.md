## Назначение

Статический код может оказаться внутри EXE и нескольких DLL. Локальные статические объекты тогда могут существовать независимо в каждом модуле. Для сервиса, которому нужно общее состояние, все модули должны обращаться к одному загруженному экземпляру его динамической библиотеки.

## Описание компонента

Необязательное поле stateScope принимает module или process. Отсутствие поля сохраняет прежнее поведение без дополнительных ограничений. module разрешает независимые экземпляры и все варианты сборки. process разрешает только Dynamic.

```json
{
  "name": "ComponentA",
  "stateScope": "process",
  "msbuildGuid": "{9C51FF34-91AE-4F32-98AE-ABBAFE4219E1}",
  "headers": ["Includes/ComponentA/UniversalDevKit/ComponentA/Service.h"],
  "sources": ["Sources/ComponentA/Service.cpp"],
  "dependencies": []
}
```

В Connect Shared/Static показываются недоступными с объяснением. При выборе без явно указанного режима process-компонент получает Dynamic. Обычный ProjectOnly допускает только Shared-корни; process-корень подключается через solution.

## Динамическая зависимость

linkage теперь принимает same, static или dynamic. same наследует вариант бинарного родителя; static требует Static; dynamic требует Dynamic независимо от варианта родителя. Для Shared same/static сохраняют подключение исходниками, а dynamic добавляет ссылку на библиотеку.

```json
"dependencies": [
  {
    "component": "ComponentA",
    "visibility": "private",
    "linkage": "dynamic"
  }
]
```

Таким образом, ComponentB.Shared компилируется в consumer, но вызывает ComponentA.Dynamic. Consumer получает импортную библиотеку, макрос импорта и runtime DLL. ComponentB.Static также требует динамический сервис на этапе финальной линковки. ComponentB.Dynamic связывается с сервисом при сборке своей DLL.

same/static не превращаются автоматически в dynamic при встрече process-компонента: несовместимая цепочка отклоняется. Контракт зависимости нужно явно исправить на dynamic.

## MSBuild

Генератор не создаёт Static.vcxproj process-компонента. Shared.vcxitems отображается в solution для просмотра и редактирования исходников собственной Dynamic-библиотеки; он проверяет, что импортирован именно её проектом. Это технический файл компиляции DLL, а не разрешённый способ подключения сервиса к consumer.

Sources.targets для ProjectOnly теперь рассчитывает смешанный граф: импортирует только Shared-файлы и добавляет ссылки, import-макросы и runtime-набор динамических зависимостей. Несовместимые варианты разных корней вызывают ошибку до компиляции. Обычный Connect использует тот же расчёт.

Если существующий компонент переведён в process, старые Static-проекты и записи solution автоматически не удаляются. Их нужно убрать при миграции, повторить генерацию и Connect для потребителей. Попытка собрать старый Static-проект блокируется проверкой внутреннего списка файлов.

## CMake

Static-target process-компонента не создаётся. При обычном выборе обоих вариантов корень получает только Dynamic. Явная статическая зависимость на него отклоняется. Если запрошен process-корень при отключённом BUILD_DYNAMIC и включённом BUILD_STATIC, конфигурация завершается ошибкой. Требуемая dynamic-зависимость обычного Static-корня создаётся даже при BUILD_DYNAMIC=OFF: переключатели регулируют корни, а не обязательные зависимости.

## Проверки и границы

Connect.Tests проверяет запреты, варианты и Shared-to-Dynamic. TestComponentRegistry проверяет генерируемые ссылки и отсутствие запрещённых проектов. Tests/Fixtures/Libraries/Registry собирает EXE и два плагина со статическим общим кодом: все три изменяют один счётчик внутри Service.Dynamic. Тест ProcessState проверяет значения 1, 2, 3.

Политика предотвращает включение реализации сервиса исходниками или статически через штатные инструменты UDK. Она не контролирует ручное копирование исходников и загрузку нескольких разных копий DLL/SO. ABI, время жизни сервиса, конкурентный доступ и выгрузка библиотеки остаются ответственностью реализации и приложения.
