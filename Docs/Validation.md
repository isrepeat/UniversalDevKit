## 1. Проверить описания без изменения файлов

Из корня репозитория:

```powershell
./Scripts/PowerShell/GenerateComponentProjects.ps1 -Check
./Scripts/PowerShell/Connect.Tests.ps1
./Scripts/PowerShell/TestComponentRegistry.ps1
```

Первая команда проверяет актуальность генерируемых проектов, зависимостей, solution и фильтров. Вторая проверяет расчёт вариантов, графы зависимостей и части меню. Третья рассчитывает добавление нового компонента без записи и проверяет платформенные элементы MSBuild. Эти проверки не заменяют сборку реального consumer.

Tests/RegistryFixture также является отдельным CMake-проектом с общим и Windows-исходником. Его можно конфигурировать через `cmake -S Tests/RegistryFixture -B !artifacts/Windows-x64/cmake/RegistryFixture` с подходящим генератором.

## 2. Проверить установленный CMake-пакет

```powershell
./Scripts/PowerShell/TestCMakePackage.ps1 -CMake 'C:/Path/To/cmake.exe'
```

По умолчанию скрипт использует Visual Studio 18 2026 x64. Он создаёт уникальное дерево !artifacts, собирает и устанавливает Debug/Release, переносит установленный prefix и собирает отдельный consumer. CTest запускает Static и Dynamic в обеих конфигурациях; неизвестный обязательный компонент проверяется ожидаемой ошибкой конфигурации.

Исходный prefix после переноса отсутствует. Проверка показывает, что установленный экспорт работает после смены пути; исходники самого тестового приложения берутся из Tests/CmakePackage. Результаты сохраняются в !artifacts для анализа.

## 3. Что ещё нужно проверять вручную

После изменения Connect пройдите интерактивное подключение, смену режима, повторный Apply, частичный и полный Disconnect. Проверьте solution с несколькими consumer: очистка одного подключения должна сохранять проекты, нужные другому.

При смене Dynamic на другой режим используйте чистый каталог запуска: Connect пока не удаляет старые DLL из OutDir. Наличие лишней DLL может скрывать ошибку расчёта runtime-набора.

## 4. Совместимость бинарников

Для Windows должны совпадать поддерживаемые архитектура, конфигурация, toolset и CRT. Для Linux важны стандартная библиотека и минимальная системная среда; для Android — ABI, NDK, API level и C++ runtime. Полная матрица выбора/проверки пакетов пока не реализована.

Публичный Log(std::string_view) использует C++ ABI стандартной библиотеки. Текущая проверка версии CMake не гарантирует совместимость произвольных бинарников. Политика API/ABI, экспорт символов вне Windows, SO VERSION/SOVERSION и выпуск NuGet/AAR остаются в TODO.

## 5. Состояние между модулями

Если один статический компонент включён в EXE и несколько DLL, каждый модуль может получить отдельное состояние. В Diagnostic таким состоянием является локальный статический mutex. Проверка вариантов подключения не превращает его в общий mutex процесса.

Для сервисов с кешами и регистрами область экземпляра задаётся stateScope: module или process; process требует Dynamic. Подробности — [общее состояние](StateScope.md). Общий экземпляр требует общей динамической реализации либо передачи сервисного объекта приложением.

## 6. Надёжность инструментов

Отпечатки JSON выявляют изменение реестра, но не заменяют Check/Repair удалённых ссылок или изменённых макросов consumer. Изменение solution/consumer пока не является единой восстанавливаемой операцией. Повторная распаковка SolutionInjector и политика хранения резервных копий также требуют доработки.

Платформенные поля реестра описывают намерение и выбор файлов. Подтверждённая поддержка Linux/Android требует настоящей сборки и запуска, а не только успешного расчёта проекта.
