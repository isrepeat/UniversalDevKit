## Проверить описания без изменения файлов

Из корня репозитория:

```powershell
./Scripts/PowerShell/GenerateComponentProjects.ps1 -Check
./Scripts/PowerShell/Connect.Tests.ps1
./Tests/Infrastructure/TestComponentRegistry.ps1
```

Первая команда проверяет актуальность генерируемых проектов, зависимостей, solution и фильтров. Вторая проверяет расчёт вариантов, графы зависимостей и части меню. Третья рассчитывает добавление нового компонента без записи и проверяет платформенные элементы MSBuild. Эти проверки не заменяют сборку реального consumer.

Tests/Fixtures/Libraries/Registry также является отдельным CMake-проектом с общим и Windows-исходником. Его можно конфигурировать через `cmake -S Tests/Fixtures/Libraries/Registry -B !artifacts/Windows-x64/cmake/RegistryFixture` с подходящим генератором.

## Проверить установленный CMake-пакет

```powershell
./Tests/Integration/Cmake/TestCMakePackage.ps1 -CMake 'C:/Path/To/cmake.exe'
```

По умолчанию скрипт использует Visual Studio 18 2026 x64. Он создаёт уникальное дерево !artifacts, собирает и устанавливает Debug/Release, переносит установленный prefix и собирает отдельный consumer. CTest запускает Static и Dynamic в обеих конфигурациях; неизвестный обязательный компонент проверяется ожидаемой ошибкой конфигурации.

Исходный prefix после переноса отсутствует. Проверка показывает, что установленный экспорт работает после смены пути; исходники самого тестового приложения берутся из Tests/Fixtures/Consumers/CmakePackage. Результаты сохраняются в !artifacts для анализа.

Тот же скрипт проверяет контракт через Tests/Fixtures/Consumers/CmakeContract: прямой и транзитивный конфликт вариантов, внутреннюю статическую зависимость DLL, конфликт при add_subdirectory, исключённый компонент и отсутствующий Dynamic-target. Отдельный Release-only пакет HeleprsTest.Static собирается и запускается; запрос Debug и попытка подключения x64-пакета из Win32 отклоняются. Отрицательные проверки требуют не только ненулевой код, но и ожидаемую диагностику.

## Проверить Android AAR/Prefab

Реальные HeleprsTest/DiagnosticTest проверяются через [AndroidPrefab.Tests.ps1](../Tests/Integration/Packages/AndroidPrefab.Tests.ps1) или [RunAndroidPrefabTests.cmd](../Tests/Scripts/RunAndroidPrefabTests.cmd). Профиль инструментов, Maven-координаты и CMake-подключение описаны в [Android AAR/Prefab](../Packages/Build/Android/README.md).

`RunAndroidPrefabTests.cmd -SkipDevice` собирает независимый APK и проверяет набор SO, единственный libc++_shared.so, private-заголовки и отказы при конфликте вариантов/static STL. Общая Android-группа включает этот build-only сценарий как AndroidPrefabBuild. Для instrumentation уберите SkipDevice и передайте Serial: только UDK_RESULT=PASS подтверждает вызов C++ API на Android. Сохранённые BuildPassed-DeviceNotRun отчёты запуск не подтверждают.

## Что ещё нужно проверять вручную

TestCMakePackage также собирает и устанавливает Tests/Fixtures/Libraries/Registry, затем проверяет Tests/Fixtures/Consumers/RequirementsPackage: C++20, threads, ws2_32 и сервисную DLL. Проверка схемы отдельно запускается командой `cmake -P Tests/Integration/Cmake/RequirementValidation.cmake`.

После изменения Connect пройдите интерактивное подключение, смену режима, повторный Apply, частичный и полный Disconnect. Проверьте solution с несколькими consumer: очистка одного подключения должна сохранять проекты, нужные другому.

При смене Dynamic на другой режим проверяйте состав runtime. Connect удаляет ранее доставленные неизменённые DLL по ownership-манифесту; изменённые и чужие файлы сохраняются. Проверка — [TestRuntimeCleanup.ps1](../Tests/Infrastructure/TestRuntimeCleanup.ps1). Чистый каталог запуска дополнительно исключает скрытые зависимости от старых файлов.

## Совместимость бинарников

Для Windows должны совпадать поддерживаемые архитектура, конфигурация, toolset и CRT. Для Linux важны стандартная библиотека и минимальная системная среда; для Android — ABI, NDK, API level и C++ runtime. Полная матрица выбора/проверки пакетов пока не реализована.

Публичный Log(std::string_view) использует C++ ABI стандартной библиотеки. Текущая проверка версии CMake не гарантирует совместимость произвольных бинарников. Текущие правила описаны в [ABI](Abi.md), [Windows NuGet](../Packages/Build/NuGet/README.md) и [Android AAR/Prefab](../Packages/Build/Android/README.md). Linux, расширенная Android-матрица и проверка экспорта ELF остаются в TODO.

## Состояние между модулями

Если один статический компонент включён в EXE и несколько DLL, каждый модуль может получить отдельное состояние. В DiagnosticTest таким состоянием является локальный статический mutex. Проверка вариантов подключения не превращает его в общий mutex процесса.

Для сервисов с кешами и регистрами область экземпляра задаётся stateScope: module или process; process требует Dynamic. Подробности — [общее состояние](StateScope.md). Общий экземпляр требует общей динамической реализации либо передачи сервисного объекта приложением.

## Надёжность инструментов

Отпечатки JSON выявляют изменение реестра, но не заменяют Check/Repair удалённых ссылок или изменённых макросов consumer. Connect сохраняет байтовые снимки solution/consumer и откатывает изменения при ошибке; после аварийного завершения доступно явное восстановление транзакции. Подробности — [Connect](Connect.md#восстановление-при-ошибке). Повторная распаковка SolutionInjector и политика хранения резервных копий также требуют доработки.

Платформенные поля реестра описывают намерение и выбор файлов. Для Android подтверждены NDK-сборка и сборка APK через реальные AAR/Prefab; запуск на устройстве ещё не подтверждён. Linux требует отдельной настоящей сборки и запуска.
