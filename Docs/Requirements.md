## Общий контракт

Требования задаются в JSON компонента и переводятся в настройки CMake/MSBuild. В первой версии поддерживаются минимальный стандарт C++, потоковая поддержка и системные библиотеки. Произвольные флаги компилятора не передаются через реестр.

```json
"requirements": {
  "cxxStandard": 20,
  "threads": true
},
"platformRequirements": {
  "Windows": { "linkLibraries": ["ws2_32"] },
  "Linux": { "linkLibraries": ["dl"] },
  "Android": { "linkLibraries": ["log"] }
}
```

requirements необязателен; по умолчанию cxxStandard=20 и threads=false. cxxStandard должен быть целым числом 20 или 23; threads — JSON boolean. platformRequirements необязателен, ключи платформ — Windows/Linux/Android. Каждый объект платформы содержит только массив linkLibraries с именами системных библиотек, без путей, макросов и флагов. Неизвестные поля и неправильные типы отклоняются обеими сборочными системами.

Стандарт языка является публичным минимальным требованием компонента. Потоки и системные библиотеки относятся к его реализации. Для публичных требований другого компонента используйте visibility=public в dependencies. Произвольные внешние пакетные зависимости, RTTI и исключения этим контрактом пока не описываются.

## CMake

ComponentRequirements.cmake проверяет JSON. ComponentDependencies.cmake применяет target_compile_features PUBLIC cxx_std_20/23, Threads::Threads PRIVATE и выбранные системные библиотеки PRIVATE. Более высокий стандарт consumer сохраняется; более низкий CMake повышает до необходимого через compile features. При отсутствии поддержки стандарта выбранным компилятором конфигурация/сборка отклоняется механизмом CMake.

Для Static системные библиотеки доходят до финального линкера через экспортированные LINK_ONLY-зависимости. Для Dynamic внутренние системные библиотеки используются при сборке DLL/SO. Config установленного пакета получает find_dependency(Threads), если Threads требуется собранным компонентам. Подключение пакета не требует отдельного ручного объявления ws2_32/pthread.

## MSBuild

Генератор добавляет элементы требований в Shared.vcxitems, Dependencies.props и Sources.targets. Обычный Connect сохраняет требования выбранного consumer вместе с библиотечными ссылками. Общий UniversalDevKit.Requirements.targets проверяет эффективный LanguageStandard каждого C++-файла перед ClCompile и добавляет системные .lib перед Link, сохраняя существующие AdditionalDependencies.

В отличие от CMake, MSBuild-adapter не меняет настройки языка существующего consumer: недостаточный стандарт вызывает понятную ошибку. Более высокий стандарт consumer сохраняется. Для новых библиотечных проектов генератор выбирает требуемый стандарт по шаблону; существующие проекты сохраняются, и при повышении требований их стандарт нужно обновить вручную. Для C++23 в новом проекте выбирается stdcpplatest.

Windows threads использует штатную поддержку MSVC/CRT без дополнительной pthread.lib. Системные имена Windows преобразуются в .lib, например ws2_32 → ws2_32.lib. MSBuild-adapter системных требований других ОС пока отсутствует и выдаёт явную ошибку вместо имитации настройки Linux/Android toolchain.

## Разные способы подключения

| Режим | Требования компиляции | Системные библиотеки |
|---|---|---|
| Shared | Исходники компилируются в consumer, учитываются также требования их зависимостей | Передаются его линкеру |
| Static | Библиотека компилируется отдельно; consumer получает публичные требования | Передаются финальному линкеру для статического графа |
| Dynamic | Реализация компилируется в DLL/SO; consumer получает публичные требования | Внутренние библиотеки связываются с DLL/SO |

После изменения JSON выполните генерацию и повторите обычный Connect, чтобы обновить сохранённый план. ProjectOnly использует заново сгенерированные Sources.targets при сборке. Архитектурные ограничения stateScope/linkage продолжают действовать.

## Проверки

DiagnosticTest теперь объявляет threads в JSON; его CMake-файл не содержит отдельной настройки потоков. Tests/Fixtures/Libraries/Registry проверяет C++20 через std::span и системную Windows-библиотеку через WSAStartup/WSACleanup. Отдельный Windows-исходник вызывается из общей реализации, поэтому его отсутствие вызывает ошибку линковки.

TestComponentRegistry проверяет нормализацию требований и генерируемые MSBuild-элементы. `cmake -P Tests/Integration/Cmake/RequirementValidation.cmake` проверяет тот же контракт CMake, включая ошибки для неизвестного требования, неверного стандарта и типа threads. TestCMakePackage дополнительно устанавливает новый компонент и собирает отдельного потребителя, у которого исходно запрошен C++17: требование C++20 передаётся из пакета.

Интерактивный Connect на изолированном Windows solution проверен для Shared/Static/Dynamic с последующей сборкой и запуском. Проверены отказ MSBuild для C++17, сохранение stdcpplatest и отказ обеих систем для неподдерживаемой ОС. Это Windows-проверки, а не подтверждение Linux/Android toolchains.
